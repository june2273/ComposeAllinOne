# 화성학 학습 파트 — 구현 계획

**작성일**: 2026-08-30 · **갱신**: 2026-09-11

> **H1·H2가 하나로 합쳐져 끝났다(2026-09-10).** 겹음정과 반음정이 따로 오는 대신
> **음정 활동 하나에 옵션 넷**(단계 · 음 범위 · 겹음정 · 표 보기)이 됐고, 예전의
> 다섯 줄(반음 계산법 · 음정표 외우기 · 온음정 · 반음정 · 겹음정)이 그 한 줄로
> 대체됐다. 계획과 실제가 갈린 자리가 둘이다:
>
> - **기반 A(조와 표기)가 반음정에 필요하지 않았다.** 조는 **음이름**만 정하고
>   임시표는 새 축 `maxAlter`가 정한다 — MIDI에서 표기를 되찾는 대신 표기에서
>   쌓아 내려가면 `natural()`이 던지는 자리를 아예 지나지 않는다. 기반 A는 조표
>   다이아토닉과 화음 근음에서 **여전히 필요하다**.
> - **성질 버튼을 7개로 늘리는 대신 없앴다.** 답이 `증5`처럼 타이핑이 됐다.
>   그래서 겹겹증·겹겹감까지 넓히는 데 화면 비용이 0이었다.
>
> 아래 H1·H2는 그때의 판단을 남겨 둔다. **H3부터가 남은 계획이다.**
>
> **옵션이 둘 더 붙었다(2026-09-11).** 계획에 없던 것이고 둘 다 값이 쌌다.
>
> - **낮은음자리표** — 음역 하한만 내린다. 자리표는 `score.clefFor`가 음을 보고
>   정하므로 옵션이 자리표를 직접 건드리지 않고, 그래서 한 세션에 두 자리표가
>   섞인다. 악보와 실제 음이 갈릴 자리가 없다.
> - **음정 해석** — 방향이 반대인 스테이지 하나(`Stage.IntervalBuild`).
>   `G4 · 장2도 · 위로`에 건반으로 A4를 누른다. 문제는 기존 생성기가 낸 음 쌍을
>   **어느 쪽을 주고 어느 쪽을 묻는가**로 나눈 것이라 새 출제 로직이 없고,
>   채점도 기존 `AbsolutePitchGrader`를 그대로 쓴다. **읽기와 쓰기를 갈라 익히는
>   자리**라 H3 이후의 화음에도 같은 방식이 쓰일 것이다.

## 0. 지금 무엇이 있고 무엇이 남았는가

카탈로그의 화성학 12항목 중 넷이 동작한다 — 음정 3단계(반음 계산법 · 음정표 외우기 ·
온음정)와 가상 피아노. 나머지 여덟이 이 계획의 대상이다.

| 활동 | 카탈로그 id | 막고 있는 것 |
|---|---|---|
| 반음정 | `harmony.interval_chromatic` | 기반 A |
| 겹음정 | `harmony.interval_compound` | **없다** — 상수 두 개와 입력 방식뿐 |
| 3화음 | `harmony.triad` | 기반 B · C · D |
| 7화음 | `harmony.seventh` | 기반 B · C · D |
| 조표 다이아토닉 | `harmony.key_diatonic` | 기반 A · B · C |
| 텐션 | `harmony.tension` | 기반 B (자료 작업이 대부분) |
| 모드 | `harmony.mode` | 기반 C · E |
| 코드 학습 | `harmony.chord_play` | 기반 G (연주형이라 나머지와 별개다) |

**청음 도메인의 `ear.chord`(화음 청음)도 같은 기반 위에 있다.** 기반 B가 서면
생성기 하나와 `makeGenerator`의 분기 한 줄로 끝난다 — 화성학 작업의 부산물이므로
같이 적어 둔다.

## 1. 순서를 정하는 것은 난이도가 아니라 막힌 기반이다

여덟 개를 난이도순으로 늘어놓으면 3화음이 앞에 오는데, 실제로 앞에 와야 하는 것은
**여러 활동이 함께 기다리는 기반**이다. 지금 막혀 있는 자리는 일곱이다.

| | 기반 | 지금 상태 | 이것이 서면 열리는 것 |
|---|---|---|---|
| **A** | 조(Key)와 표기 | `theory.natural()`이 검은건반에서 던진다. `DiatonicIntervalGenerator`가 그것을 부르므로 **C장조 밖으로 나갈 수 없다** | 반음정, 조표 다이아토닉, 화음 전체의 근음 |
| **B** | 화음 자료구조 + 화음 응답 폼 | `requiredPcs`/`optionalPcs`와 `PitchClassGrader`는 **이미 규칙까지 구현돼 있다**. 없는 것은 화음 정의 표와 응답 폼 | 3화음, 7화음, 텐션, 조표 다이아토닉, 화음 청음 |
| **C** | 3음 이상 악보 | `score.harmonicIntervalMusicXml(a, b)` — 정확히 두 음 전용이다 | 화음 전부, 모드(음계) |
| **D** | 이명동음 가드 | 사양서 3절의 A+C 방침이 **문서에만 있다** | 7화음(dim7 4종), 3화음(aug 3종), 텐션 |
| **E** | 순차 입력 채점 | `NoteCollector`가 집합처럼 쓰인다 — 순서는 보존하지만 **중복을 버리고**, 채점기가 없다 | 모드·스케일 |
| **F** | 기록 저장소 + 태그 UI | `Session.tagFilter`는 **이미 돈다**(`session.draw()`). 화면과 저장소가 없다 | 집중연습·오답노트 — 전 활동 공통 |
| **G** | 트랜스포트 시계 | 없다 | 코드 학습 |

기반 A·B·C 셋이 여섯 활동을 막고 있고, 겹음정 하나만 그 밖에 있다.
**그래서 겹음정이 첫 번째다** — 기반을 하나도 안 건드리면서 두 자리 입력이라는
숨은 함정을 먼저 드러낸다.

## 2. 단계별 계획

### H1 — 겹음정 (기반 없음 · 작음) — **끝남 2026-09-10**

`theory.intervalBetween()`이 9·10도를 이미 정확히 계산한다. 상수와 음역만 넓히면
된다 — **다만 화면 입력에 함정이 하나 있고, 그것이 이 단계의 실제 내용이다.**

- `DiatonicIntervalGenerator.MAX_NUMBER` 8 → 13, 음역 상한 A5(81) → E6(88).
  2옥타브가 있어야 13도 쌍이 만들어진다.
- **도수 입력을 Enter 제출로 바꾼다.** 지금 `IntervalStage`는 "성질과 도수가 다 차면
  즉시 제출"인데, 도수가 두 자리가 되는 순간 **9를 치려다 1에서 제출된다.**
  `stages.tsx` 머리말이 이 함정을 이미 경고하고 있다("여러 자리 숫자를 받는 칸이
  있으면 '칸이 다 차면 제출'을 쓸 수 없다"). 연습 1(`IntervalCountStage`)이 쓰는
  Enter 제출 방식을 그대로 가져온다.
- 홑음정 환원("9도 = 2도 + 옥타브")은 **오답 진단 문구**로 낸다. 별도 입력 칸을 만들면
  묻는 것이 둘로 늘어나 본 단계가 아니라 연습이 된다.
- 채점기는 `IntervalGrader` 그대로. 새 `Stage` 하나(`IntervalCompound`)와
  `makeGenerator` 분기 한 줄.

손대는 곳: `config.ts`(Stage + 설정 상수) · `questions.ts`(분기) · `stages.tsx`(제출 방식) ·
`catalog.ts`(status). **`session.ts`·`grading.ts`는 안 바뀐다.**

회귀 시험: 두 자리 도수를 눌러도 중간에 제출되지 않는가(`pressAll` 방식),
9~13도의 이름이 `intervalBetween()`과 일치하는가.

### H2 — 기반 A: 조와 표기 → 반음정 (중간) — **반음정만 끝남 2026-09-10.** 기반 A는 안 만들었고 필요하지도 않았다

`core/harmony/key.ts`를 새로 판다. `core/`의 순수 로직이고 React·브라우저를 모른다.

```ts
interface Key { tonic: string; alter: number; mode: "major" | "minor" }
scalePitches(key, octave): Pitch[]     // 표기가 붙은 음계음
fifths(key): number                    // 조표 (♯ 양수 / ♭ 음수)
spell(key, midi): Pitch                // 그 조에서의 표기
```

- **`natural()`을 대체하는 것이 요점이다.** 생성기가 MIDI 번호에서 표기를 되찾는 대신
  **조에서 음계음을 만들어 내려오면** 임시표가 자연스럽게 따라온다. 이 방향을 뒤집지 말 것 —
  MIDI에서 표기를 유도하려는 순간 이명동음 문제가 여기까지 올라온다.
- **조표 표가 세 벌이 된다.** 지금 `analysis/key.keyFifths`와 `transcribe/musicxml.keyFifths`가
  두 벌이고 회귀 시험이 24개 조에서 대조하고 있다. 층 규칙이 셋을 잇는 것을 금지하므로
  **그 시험을 3자 대조로 넓힌다.**
- **난이도 축은 갈아엎지 않는다.** `DifficultyAxes.key`를 추가하고
  `allowedPitchClasses`는 거기서 유도한 값으로 채운다. `axesAllow()`와 기존 세
  스테이지가 한 줄도 안 바뀐다. (CLAUDE.md의 "조에서 유도하도록 바꿔야 한다"에 대한 답이다 —
  치환이 아니라 **유도**로 간다.)

반음정은 그 위에 얹힌다.

- 성질 버튼 5개 → 7개. `stages.QUALITIES` 한 배열이 답 값·원어 이름·단축키를 함께
  들고 있으므로 **두 줄을 더하면 선택지·키캡·채점이 함께 따라온다.**
  단축키는 증(`A`)·감(`D`)의 오른쪽에 붙여 **겹증 `S` · 겹감 `F`** — 손 위치가 이어지고,
  대소문자로 가르지 않는다는 기존 규칙을 지킨다.
- **`diatonicHalfSteps`를 여기서 재사용하지 않는다.** 임시표가 붙으면 교재의 반음
  셈법 자체가 성립하지 않는다(E♭–F는 온음). 함수가 던지고, 그것이 맞다.
  **반음정에는 연습 1·2에 해당하는 단계가 없다** — 그 둘은 온음계 표에 매인 장치다.
- 이명동음 위험은 **없다.** 문제를 악보로 보여주고 화면 폼으로 답하므로 표기가
  문제 안에 이미 있다. 위험은 건반으로 답하는 스테이지에서만 생긴다(기반 D).

### H3 — 기반 B·C·D: 3화음 → 7화음 (큼 · 이 계획의 중심)

**`core/harmony/chords.ts`** — 화음 정의를 데이터로 둔다.

```ts
interface ChordSpec {
  quality: string;                  // 장·단·증·감 / maj7·m7·7·m7♭5·dim7
  degrees: readonly [number, number][];  // [도수, 성질오프셋] — 근음에서 쌓는다
  required: readonly number[];      // 생략 불가 도수
  optional: readonly number[];      // 생략 허용 (텐션에서 쓴다)
}
chordPitches(root: Pitch, spec, inversion): Pitch[]
```

근음에서 **도수로 쌓기** 때문에 표기가 저절로 옳게 나온다. C에서 증5도를 쌓으면 G♯,
D♭에서 쌓으면 A♮ — MIDI 번호로 쌓았다면 둘 다 그냥 검은건반이다.

**`score.chordMusicXml(pitches, fifths)`** — 기존 `noteXml`을 그대로 쓰고 둘째 음부터
`<chord/>`를 붙인다. 음자리표는 최저음이 `BASS_CLEF_BELOW` 아래인지로 고른다.
`harmonicIntervalMusicXml`을 이 함수의 특수 사례로 다시 짜고, **두 출력이 문자 단위로
같은지 보는 회귀 시험**을 붙인다 — 그러지 않으면 음정 그림이 조용히 달라진다.
`<note>`의 자식 순서(pitch → duration → tie → type → dot → accidental)는 규격이고,
어기면 verovio가 그 음표를 소리 없이 흘린다.

**응답 폼과 채점기.** `StageResponse`에 `{ form: "chord", root, quality, inversion }`를
더한다 — 필드 유무가 아니라 `form`으로 가르는 기존 규칙 그대로다.
`ChordSymbolGrader`는 셋을 각각 보고 **어느 축이 틀렸는지 짚어 준다**(음정 3단계의
진단 문구와 같은 방침: 근음이 틀렸다 / 성질이 틀렸다 / 전위만 틀렸다).

**성질 버튼을 음정과 공유하지 않는다.** 장·단·증·감이라는 글자는 같지만 음정의 성질과
화음의 성질은 다른 축이다. `TRIAD_QUALITIES`를 따로 둔다 — 화면이 같아 보이는데 값이
다른 축에 실리는 것이 이 저장소에서 가장 찾기 어려운 종류의 오류다.

**기반 D — 이명동음.** 사양서 3절의 A+C를 여기서 처음으로 실제로 구현한다.

- **A**: 채점은 음고류로 하고 **정답 스펠링을 화면에 보인다.** `Question.answerText`가
  이미 그 자리다.
- **C**: `EnharmonicGuard` — 한 세션 안에서 **같은 음고류 집합을 다른 표기로 두 번 내지
  않는다.** 생성기가 낸 문제의 pc 집합 서명을 기억하고 충돌하면 다시 뽑는다.
  걸리는 것은 감7화음 4종, 증3화음 3종, 그리고 뒤에 증6화음이 들어오면 `Ger65`/`A♭7`이다.
- `Session.draw()`가 이미 태그 필터로 64번까지 재추첨하므로 **같은 자리에 얹으면 된다.**

7화음은 `ChordSpec` 표에 다섯 줄을 더하는 일이다. 새 코드는 거의 없다.

### H4 — 조표 다이아토닉 (중간)

기반 A와 B 위에 얹힌다. verovio는 `<key><fifths>`를 이미 그린다.

묻는 방향이 둘이고 **둘 다 같은 문제 자료에서 나온다** — "이 조의 V7은?"(로마자 → 화음)과
"이 화음은 이 조에서 몇 번째인가?"(화음 → 로마자).

> **로마자 라이브러리는 넣지 않는다.** music21은 파이썬이라 웹에서 못 쓰고, JS 대안
> (`tonal`)을 들여도 지금 얻을 것은 **표 한 장**이다 — 장조 `I ii iii IV V vi vii°`와
> 단조 3종. 차용화음·부속7화음·증6화음까지 갔을 때 다시 판단한다. 그때 필요한 것은
> 표가 아니라 **분석**이므로 판단 근거가 실제로 달라진다.
> (카탈로그의 `requires`에 적힌 "여기서 검토할 것"에 대한 답이다.)

### H5 — 텐션 (중간 · 자료 작업이 대부분)

`requiredPcs`/`optionalPcs`와 `PitchClassGrader`가 **사양서 5절의 생략음 규칙을 이미
구현하고 있다.** 필수음이 다 있고 군더더기가 생략 가능음 안이면 통과 — 채점기는 한 줄도
안 바뀐다. 할 일은 `ChordSpec` 표를 채우는 것이다(♭9·♯9·♯11·♭13, 근음·3음·7음·해당
텐션이 필수, 5음·9음이 생략 가능).

**여기서 처음으로 건반 입력이 본류가 된다.** 6음 화음을 화면 폼으로 고르게 할 수 없다.
`chordHoldMs`를 70으로, 넓은 보이싱 연습에는 아르페지오 모드(500~800ms)로 둔다 —
**입력 그룹핑은 이미 동작하므로 설정값 문제다.**
어보이드 노트는 채점이 아니라 표시다(틀렸다고 하면 안 된다).

### H6 — 모드 (중간 · `session.ts`를 건드리는 유일한 단계)

`NoteCollector`가 순서를 보존하기는 하지만 **중복을 버린다** — 상행 후 하행하면 꼭대기
음이 사라진다. 확정 규칙도 다르다(마지막 note-on 이후가 아니라 **건반을 전부 뗐을 때**).
그래서 `SequenceCollector`를 따로 두고 `SessionConfig`에 축 하나
(`inputForm: "set" | "sequence"`)를 더해 `Session`이 그것으로 수집기를 고른다.

> **이것이 "`core/session.ts`는 바뀌지 않아야 한다" 규칙을 건드리는 두 번째 자리다**
> (첫 번째는 일시정지). 스테이지가 는 것이 아니라 **입력의 형태 자체가 는 경우**라
> 예외로 볼 근거는 있지만, 값싸게 넘기지 말고 그때 다시 판단할 것.

특성음 강조 재생은 `AudioBackend.playSequence`가 이미 준다(악보 재생용으로 들어온 것).
`SequenceNote.velocity`가 음마다 다를 수 있으므로 특성음만 세게 내는 데 새 인터페이스가
필요 없다.

### H7 — 코드 학습 (연주형 · 기반 G · 큼)

**재료가 이미 다 있다는 것이 이 항목의 요점이다.** 분석 콘솔이 오디오 파일 하나에서
`ChordEvent[]` · 비트 · 다운비트를 낸다. 사용자가 자기 음원을 넣으면 **연습 데이터가
그대로 나온다** — 곡 데이터를 손으로 적을 필요도, 음원을 배포할 필요도 없다.
카탈로그가 걱정한 저작권 문제가 이 경로에서 사라진다.

- **`Session`을 쓰지 않는다.** 문제 큐가 아니라 연속 타임라인이고, 판정이 정답/오답이
  아니라 빗나간 밀리초다.
- **기준 시계는 `AudioContext.currentTime`이다.** `requestAnimationFrame`은 화면 갱신용이고
  판정에 쓰면 드리프트가 그대로 점수가 된다.
- **`MidiHandlers.onNoteOn`의 `timeStamp`로 판정한다.** 도착 시각으로 재면 메인 스레드
  지연이 점수에 섞인다 — 이 값을 이미 넘기고 있는 이유가 이것이다.
- 화면은 `ActivityScreen`이 `Kind.Performance`에서 고른다. 도구가 `Kind.Tool` 안에서
  id로 갈리는 것과 같은 방식.

### H8 — 기록과 집중연습 (전 활동 공통 · 마지막)

`Session.tagFilter`가 이미 돌고 생성기들이 태그를 성실히 붙이고 있다. **없는 것은
화면과 저장소뿐이다.**

- `session.Result`를 넘겨받는 포트 하나로 가른다 — 웹은 IndexedDB, Tauri는 SQLite.
- 오답노트 → Leitner 박스 3~5개. 사양서 9절 Phase 4.
- 이것을 앞으로 당기지 말 것. 활동이 늘기 전에 만들면 **무엇을 기록해야 하는지 모르는
  채로 스키마를 정하게 된다.**

## 5. 이 계획이 무엇으로 검증되는가

오디오 분석 쪽과 **판정 장치가 다르다.** 거기서는 정답이 사람의 채보라 평가셋이
필요했지만, 화성학은 **정답이 정의상 확정된다** — `theory.intervalBetween()`이
계산하는 것이 곧 정답이다. 그래서 여기서 값을 하는 것은 평가셋이 아니라 회귀 시험이고,
특히 아래 셋이다.

1. **손으로 옮겨 적은 표는 반드시 `theory`와 대조한다.** 음정표(`PERFECT_TABLE`·
   `MAJOR_MINOR_TABLE`)가 C4~C6 온음계 92쌍 전부를 대조하고 있다. `ChordSpec` 표와
   다이아토닉 로마자 표도 같은 취급을 받아야 한다.
2. **같은 것을 두 곳에서 계산하면 두 곳을 대조한다.** 조표 표가 셋이 되므로 24개 조에서
   세 값이 같은지 본다.
3. **화면 입력은 "한 태스크에 묶여 들어오는" 경우를 시험한다.** 숫자와 버튼이 같은
   태스크에 들어오면 마지막 입력이 빈 상태를 보는 사고가 이미 한 번 났다(`pressAll`).
   겹음정의 두 자리 입력과 화음의 세 축 입력이 정확히 그 모양이다.

**측정 없이 "쉬워졌다/정확해졌다"를 말하지 않는다**는 규칙은 여기서도 그대로다. 다만
화성학에서 그 측정은 정확도가 아니라 **시험이 도는가**이다.
